5.GitHub -> Actions -> 05-Stage Blue Green 

<img width="2920" height="730" alt="image" src="https://github.com/user-attachments/assets/6866dd4a-257a-4bfd-b07a-a6e2e5a04ccc" />

If BLUE is currently ACTIVE in STAGE, we should deploy the new v1.1.0 to GREEN, not BLUE.

The safe blue/green flow is:
BLUE = ACTIVE (current production-like version)
GREEN = INACTIVE (candidate)
        ↓
Deploy v1.1.0 → GREEN
        ↓
Health/readiness check
        ↓
Test GREEN
        ↓
Switch Service selector
BLUE → INACTIVE
GREEN → ACTIVE
So for STAGE, select:

* Image tag: v1.1.0
* Target color: green

The workflow should not touch the active BLUE deployment until GREEN is healthy.

After workflow passed, the tag version is updated in Stage Green

BLUE becomes a candidate environment. We can run automated checks against BLUE without exposing users to it:

 Pod health
    * Ready/Running
    * restart count
    * readiness/liveness
 Smoke tests
    * /health
    * /
    * payment API test
 Deployment validation
    * Correct image digest
    * Correct version
    * Correct environment variables/config
 Security checks
    * Trivy image scan
    * vulnerability threshold
 Performance test
    * BlazeMeter/load test against BLUE
 Observability validation
    * Prometheus metrics available
    * expected latency/error rate
 AI-SRE validation later
    * Agent investigates BLUE
    * compares BLUE vs GREEN
    * identifies anomalies
    * gives GO / NO-GO recommendation
